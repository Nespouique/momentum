# Story 3.8: Daily Home Navigation

## Status: done

Implementation is complete. The user reports that manual acceptance testing is OK and accepts the
story based on that overall feedback. This is not a scenario-by-scenario test report, a formal BMAD
code review, or evidence of a production deployment; see [Verification Notes](#verification-notes).

## Story

**As a** user,
**I want** to navigate the home dashboard one day at a time and edit a past day's habits,
**so that** I can review and correct my daily tracking without changing interfaces.

## Acceptance Criteria

### 1. Preserve the existing home (FR29, FR35)

**Given** the current home dashboard,
**When** this feature is added,
**Then** only two icon buttons, previous day (`<`) and next day (`>`), are added at the top,
**And** the existing layout, components, ordering and actions remain unchanged except for date-dependent content.

### 2. Navigate one calendar day (FR30)

**Given** a fresh opening of the home initialized to today,
**When** the user activates the previous-day button or the enabled next-day button,
**Then** the selected date moves exactly one calendar day backward or forward,
**And** navigation works across month, year, leap-day and daylight-saving boundaries without date shifts.

### 3. Prevent navigation into the future (FR31)

**Given** today is selected,
**When** the navigation controls are rendered,
**Then** the next-day button is visibly grayed out and actually disabled for pointer and keyboard activation,
**And** from a past date it remains enabled until the user returns to today, where it becomes disabled again.

### 4. Render the selected day's home (FR32, FR36)

**Given** a past date is selected,
**When** its data is displayed,
**Then** the existing date display, tracking values, completion states and daily progress represent that selected day,
**And** the dashboard uses currently configured habits and goals, not a historical configuration snapshot,
**And** any existing date-dependent home content uses the selected day as its reference date without adding new components.

### 5. Exclude later accomplishments (FR36)

**Given** a habit was checked on a date later than the selected day but was not checked on the selected day,
**When** the selected day's dashboard is rendered,
**Then** the habit appears unchecked for that day and remains in the configured list,
**And** existing period counters exclude accomplishments dated after the selected day.

### 6. Correct past daily entries (FR33, FR34)

**Given** a habit is editable under the current home rules,
**When** the user checks or unchecks a boolean habit, or saves a numeric or duration value for a past selected day,
**Then** the edit is persisted for that selected day only and the displayed values and completion state are updated,
**And** other days' entries are unchanged,
**And** the saved edit remains when the user leaves and revisits that day, including after reloading and navigating back.

### 7. Preserve current action semantics (FR35)

**Given** a past day's dashboard is being viewed,
**When** the user interacts with existing home actions,
**Then** existing editing restrictions for synchronized and calculated data remain unchanged,
**And** existing workout-start actions retain their real execution date rather than backdating a session to the viewed date,
**And** both planned and ad_hoc workout sessions continue to be supported.

### 8. Isolate asynchronous reads and edits by date (FR34)

**Given** rapid day navigation or a pending save,
**When** an earlier request completes after the selected date has changed,
**Then** its response cannot replace another day's displayed data and its mutation stays associated with the original edited date,
**And** loading and errors use the existing home feedback patterns without presenting another day's values as the selected day's data,
**And** a failed save does not simulate successful persistence and any optimistic change is rolled back for its original date.

### 9. Accessible and visually consistent controls (FR29, FR31, FR35)

**Given** the two icon buttons are displayed on mobile or desktop,
**When** they are used by pointer, touch, keyboard or assistive technology,
**Then** their accessible labels are "Jour précédent" and "Jour suivant", enabled buttons have visible focus and keyboard activation, and touch targets follow the existing UX target of 48 px,
**And** the controls respect the current dark theme and user accent variables without hardcoded brand colors.

## Dev Notes

- This is an incremental extension of Epic 3, not a dashboard redesign. Do not add a return-to-today button, date picker, calendar, new section, changed CTA or new read-only policy.
- The baseline is the implemented home, not old wireframes. Verify the current code before choosing affected files or API changes.
- Reuse existing authenticated date-based reads and daily upserts where possible. Keep one entry per `(trackableId, date)` and enforce user ownership and current input validation.
- Use the application's existing calendar-date conventions consistently. The API's date-only key must represent the viewed day, not a UTC conversion that shifts a local day. Do not introduce a new timezone preference as part of this story.
- Product-owner clarification after IR: the browser's local calendar is authoritative for this feature's today, initial selected day, future-navigation cap, and completion-day boundaries. Send the selected `YYYY-MM-DD` key explicitly; never replace it with API-local today or derive it by truncating a UTC ISO timestamp.
- For timestamp-based counters, use the browser-local start of the selected day and start of the next calendar day as a half-open interval `[start, nextStart)`, serialized as UTC instants for API filtering. Apply the same calendar convention to week/month start and selected-day cutoff. Advance calendar dates rather than adding 24 hours; DST days may contain 23 or 25 hours. Count eligible completed sessions by `completedAt`, without changing their stored execution timestamps or introducing a persisted timezone preference.
- Refresh browser-local today and its navigation cap at local midnight and on focus/visibility resume. A fresh opening initializes to today; refreshing the cap must not automatically advance a viewed day or retarget an open editor or pending mutation. Recheck the cap on navigation. Browser-dependent initialization must not produce conflicting server/client date headings during hydration.
- Disagreement fixture: at `2026-10-10T22:30:00Z`, a browser in `America/Los_Angeles` initializes to `2026-10-10` even if the API in `Europe/Paris` considers today to be October 11. Heading, reads, writes, and disabled next-day control use October 10. That browser-local day's timestamp interval is `[2026-10-10T07:00:00Z, 2026-10-11T07:00:00Z)`.
- "Exclude later checks" concerns the dates of the activities represented by entries, not the time at which an entry was created or corrected. A correction entered today for a past day must be included in that past day.
- Use current configured habits and goals. Do not reconstruct historical activation state, ordering or goal versions. A habit checked only later stays visible but incomplete on the earlier day.
- For any existing week/month counters, use the period containing the selected day and cut off qualifying entries at that day. Do not display later accomplishments as already achieved.
- Browsing a past day must not write data by itself. Missing entries use the existing home defaults and are created only by an explicit user edit.
- Preserve Health Connect source metadata, synchronization overwrite rules and the current home's editing restrictions. Do not invent manual-over-sync priority rules.
- Computed workout counts remain based on existing eligibility and date-attribution rules. Support `planned` and `ad_hoc` sessions with nullable `workoutId` and `workout`.
- Snapshot an edit's date when initiating the action. Separate selected-day state from pending requests; never read a newly selected date to identify a previously submitted mutation.
- No arbitrary historical navigation limit is requested; respect any existing applicable date/data constraints instead of adding a new product limit.
- Older PRD/architecture examples contain obsolete stack versions, React Query assumptions, API prefixes and routing. Follow current repository conventions; introducing React Query is not required.
- No new table, historical configuration storage, migration, scaffolding or infrastructure change is expected. Only change API logic if current contracts cannot meet the approved date behavior.

### Implementation Notes — Mutation and Async Isolation

- Reads are keyed by session token, user ID and selected date; request generations prevent late A-B-A responses from presenting stale data. Rendering checks response ownership and selected date. Per-date snapshots retain edits through navigation, while fresh dates display no stale response.
- Both boolean and numeric writes receive the date captured at interaction/editor opening and the token/user are rechecked against current auth before persistence. Numeric editor key includes user/date/trackable; Enter/blur submits once, Escape cancels, and failed persistence leaves the editor available for correction/retry.
- Optimistic changes are stored by owning user/date; rejected writes restore only their original trackable/date snapshot, independent of a recovery GET. Concurrent pending changes to another trackable are not overwritten by rollback. A per-trackable write gate blocks duplicate requests.
- Test suites after this group passed: API 9 tests and web 8 tests; `npm run lint` and web/API no-emit TypeScript checks succeeded. API build was not repeated during the review-fix run. Browser validation remains outstanding as described below.

### Review Fixes

- Fixed rollback snapshots in the edit ledger: a failed write restores the captured original trackable value even when GET recovery fails; a different successful trackable is committed independently.
- Background refresh keeps selected-date cards mounted and retains their local numeric draft. The dashboard only renders data keyed to the selected date; refresh errors retain same-date data.
- Boolean and numeric write refusal returns failure to the card; numeric draft stays open for retry. Draft numeric values are kept in date/user/trackable keyed page state so navigation/remount does not discard them. In-flight writes are exposed to date-keyed remounted cards and duplicate submissions are refused explicitly.
- API query validation now relates day instants to the selected date, requires browser-midnight instants consistent with plausible local UTC offsets, and requires exact selected-day Monday/month-start date keys. DST day intervals from 22–26 hours are accepted, including Lord Howe's half-hour transitions.
