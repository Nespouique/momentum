# Story 6.1: Authenticated MCP Server for Personal Analytics

## Status: Ready for Review

## Story

**As a** Momentum user,
**I want** to connect ChatGPT, Claude, Claude Code, OpenCode or any MCP-compatible agent to my Momentum account,
**so that** I can quickly ask natural-language questions about my sessions, favorite exercises and performances, and generate dashboards or summaries from my own production data.

## Scope

- Deliver a remotely accessible, authenticated, **read-only** MCP server for personal analytics, served by the existing API.
- Two authentication modes with the same read-only scope:
  - **OAuth sign-in** with the existing Momentum email/password for interactive clients (ChatGPT web/desktop, Claude web/desktop, Claude Code, OpenCode).
  - **Personal access tokens** created in Settings for agents, CLIs and scripts that prefer a static bearer header.
- Cover workout history, exercise performances, body measurements and daily tracking available in Momentum.
- Return structured, traceable data that the connected LLM turns into French answers, charts, dashboards and summaries in its own interface.
- Persisting generated dashboards inside Momentum and creating/modifying workouts through the LLM are separate future stories (see `docs/improvments.md`).
- Reusing an already authenticated Momentum browser session to skip the login form is out of scope: the authorization page always asks for credentials.

## Acceptance Criteria

### AC1 — Remote MCP connection

1. A documented HTTPS endpoint exposes MCP over Streamable HTTP in the production deployment (`<MCP_PUBLIC_URL>/mcp`). The server is stateless and answers in JSON.
2. A compatible client can initialize the connection, discover tools and invoke them.
3. Protected MCP requests without valid authentication return HTTP 401 with `WWW-Authenticate: Bearer resource_metadata="…"`; public discovery metadata contains no user data.
4. The connection is verified with the MCP SDK client and recorded for the Inspector and at least one actual LLM client (name, version, supported authentication flow) before production sign-off.

### AC2 — Sign in with a Momentum account

1. Adding the server to a compatible client opens a Momentum authorization page where the user signs in with their existing email and password.
2. The page identifies the requesting client and the read-only access requested, with French "Autoriser" and "Refuser" actions.
3. Authorization uses an OAuth authorization-code flow with PKCE S256, strict redirect URI validation, dynamic client registration and authorization-server/protected-resource metadata discovery.
4. Passwords are entered only on Momentum's authorization page, never in a conversation, MCP tool arguments or client configuration.
5. Cancelling authorization or providing invalid credentials never grants data access; login attempts are rate limited.

### AC3 — Scoped and revocable access

1. Access is bound to the authenticated user, the MCP resource (`resource` parameter validated) and the single read-only scope `momentum:read`.
2. Every protected request validates the token (hashed lookup), expiry, scope and the connection's revocation state.
3. Expired, revoked or unknown tokens are rejected; refresh tokens and web JWTs are never accepted on `/mcp`.
4. Momentum settings list authorized connections (OAuth clients and personal tokens) with name, creation, last use and expiry, and allow immediate revocation. Because every request is validated, a revoked connection fails on its next call.
5. Access tokens last 1 hour; refresh tokens last 30 days, are rotated on use and reuse revokes the connection. Authorization codes are single-use and short-lived (replay revokes the resulting connection). Personal tokens expire after 30 days, 90 days, 1 year or never (user's choice). Only SHA-256 hashes are stored, and tokens/passwords are never logged.
6. The MCP session id is never authentication (the server is stateless).

### AC4 — User data isolation

1. All reads and aggregates derive ownership from the authenticated token context; tools never accept a caller-supplied `userId`.
2. Session, workout, measurement and trackable reads are filtered by the authenticated user, including nested relations and aggregates; a foreign session id looks like a missing session.
3. User A cannot retrieve or infer user B's data by changing an identifier or filter; no response cache is shared.
4. The shared exercise library may be returned; performance history is always per user.
5. Responses contain only fields needed for the analysis, excluding password hashes, authentication secrets, e-mail addresses and unrelated identifiers.

### AC5 — Workout and performance questions

1. Tools list/filter sessions, return session details, search exercises and return exercise history, favorites, records and muscle-group breakdowns.
2. Filters support periods, exercise/workout identifiers and pagination. Exercise-name lookup returns candidates instead of silently choosing between several matches.
3. Session data includes date, type (`planned`/`ad_hoc`, nullable workout), status, duration, exercises and actual per-set repetitions/weights **always paired with their targets** (per set, per exercise `target` summary with sets met, volume vs target, and period `targets` in the summary).
4. Metrics reuse Momentum's definitions: volume and estimated 1RM (Epley) use actual results, never targets; bodyweight exercises expose repetitions rather than a zero load.
5. Aggregates use completed sessions and exclude skipped/substituted exercises and sets without result; other statuses stay queryable and are counted separately.
6. Questions such as « Combien de séances ce mois-ci ? », « Quels sont mes exercices préférés ? » and « Comment a évolué mon développé couché ? » are answerable from tool results without inventing data.

### AC6 — Dashboard datasets and summaries

1. Tools return period summaries and time series (day/week/month) for session frequency, duration, volume, exercise progression, muscle groups, body measurements and daily tracking.
2. Period comparisons give both periods, sample counts and deltas.
3. Results include effective period boundaries, timezone, units and metric `definitions`; list results include totals and pagination, aggregates indicate truncation.
4. Calendar periods use an explicit IANA timezone (default `Europe/Paris`), half-open timestamp bounds and DST-safe day boundaries; date-only records keep their calendar date.
5. Missing values stay `null`/distinguishable from zero; empty or truncated results are explicit.
6. Tools expose typed input schemas and annotations; structured results come with human-readable definitions. The server also publishes usage instructions and two prompts (`synthese_mensuelle`, `dashboard_performances`).
7. In a verified LLM client, « Fais une synthèse de mon mois » and « Génère un dashboard de mes 3 derniers mois » are grounded in the returned data (pending verification with an actual client).
8. No server-side OpenAI key is needed.

### AC7 — Bounded production reads

1. Access goes through typed, allowlisted read operations over Prisma; no SQL, shell, database credentials or write tools are exposed.
2. Inputs are validated with documented bounds (periods ≤ 10 years, page size ≤ 50, session cap per request with a `truncated` flag, 200 000-character response cap, 20 s timeout).
3. Rejected or oversized requests return actionable errors rather than partial silent results.
4. Rate limits (120 requests/min per connection, dedicated limits on registration, login and token endpoints) protect the production API; internal errors are not leaked.
5. Metadata logs record tool, user, connection, outcome and latency, never credentials or datasets.
6. All tools advertise `readOnlyHint`.

### AC8 — Deployment and onboarding

1. Deployment documentation covers the MCP URL, HTTPS/reverse-proxy routing, metadata URLs, environment variables (`MCP_PUBLIC_URL`, `TRUST_PROXY`, `MCP_DEFAULT_TIMEZONE`) and checks. The feature stays disabled in production until `MCP_PUBLIC_URL` is set.
2. A French guide ([mcp-server.md](../features/mcp-server.md)) explains connecting ChatGPT, Claude, Claude Code and OpenCode, revoking access, sample questions, and which data the LLM provider receives.
3. Local verification uses a disposable migrated database; production verification is read-only and recorded separately.

## Dev Notes

- Routes live in `apps/api/src/routes/mcp*.ts`, domain code in `apps/api/src/mcp/`. They are mounted in `index.ts` before the global CORS/body parsers and before the `/` progression router, with their own CORS policy (`*`, bearer only).
- Opaque tokens (`mat_`, `mrt_`, `mpt_`) rather than JWTs give instant revocation; authorization tickets are signed with a derived key so they never verify as web JWTs. `authMiddleware` now also rejects JWTs without a `userId`.
- Public clients only (`token_endpoint_auth_method: none`) with dynamic client registration, which ChatGPT and Claude support; OAuth Client ID Metadata Documents are not implemented.
- Infrastructure is not changed by this story: `MCP_PUBLIC_URL` and the NPM host must be configured at deployment (see guide). No Docker Compose repository changes were made.
- Follow-ups: LLM-driven session creation (write scope), saving dashboards, Health Connect activities as an extra tool.
